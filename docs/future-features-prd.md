# SubtitleMate 未来功能规划 PRD

> 文档生成时间：2026-08-10
> 来源：基于 `subtitlemate-ai-prompt.md` 中的 Future Features Direction 与品牌定位整理
> 目标：把 AI prompt 中的方向性描述转化为可评估、可排期的产品需求文档

---

## 一句话总结

SubtitleMate 的未来功能应围绕「从自动字幕工具升级为视频语言学习助手」展开：双语字幕模式解决「边看边学」的同步需求，单词点查解决「即时理解」的词汇需求，AI 视频总结解决「课后复习」的结构化需求。三项功能均依赖当前已落地的「操作 YouTube Player 内部对象」技术路线，但实现复杂度依次递增，建议按「双语字幕 → 单词点查 → AI 总结」的顺序分阶段推进。

---

## 背景与产品定位

SubtitleMate 当前的定位是：

> A tiny smart assistant that removes annoying repetitive clicks and makes global content easier to understand.

它通过自动启用 YouTube 字幕并按用户偏好翻译，减少观看国际内容时的重复操作。下一步的产品升级方向是把「减少操作」延伸到「增强理解」——让用户不仅能看懂视频，还能在观看过程中学习语言、积累词汇、提炼要点。

---

## 当前核心功能（基线）

| 功能 | 状态 | 说明 |
|------|------|------|
| 自动开启字幕 | 已落地 | 进入 YouTube 视频页后自动启用字幕 |
| 自动翻译字幕 | 已落地 | 按 `sm_targetLang` 自动翻译为指定语言 |
| 英语（自动生成）字幕模式 | 已落地 | 不翻译，直接启用英语自动生成字幕 |
| SPA 切换适配 | 已落地 | 监听 `yt-navigate-finish`，视频切换后重置状态 |
| Popup 设置面板 | 已落地 | 开关 + 字幕模式 + 目标语言选择 |

## 未来功能一：Dual Subtitle Mode（双语字幕模式）

### 问题

当前字幕只显示一种语言。对语言学习者来说，理想状态是同时看到原文字幕和翻译字幕，以便对照学习。

### 目标

在同一视频画面上同时显示两行字幕：

- 第一行：原文字幕（如 English）
- 第二行：目标语言翻译（如 中文）

### 用户故事

- 作为一名英语学习者，我希望在观看 YouTube 视频时同时看到英文原句和中文翻译，以便理解内容的同时学习表达。
- 作为一名日语学习者，我希望原生日语字幕和中文翻译同时出现，避免频繁切换字幕语言。

### 需求

#### Must-Have（P0）

1. 在 popup 中新增「双语字幕」开关。
2. 当双语模式开启时，扩展在原有翻译字幕之外，额外渲染一行原文字幕。
3. 原文字幕取自可用的原生字幕轨（优先 `en/asr` 或视频原语言轨）。
4. 两行字幕在视觉上有明显区分（如颜色、字号、位置偏移）。
5. 双语模式仅在当前视频存在至少一条原生字幕轨时可用；否则提示用户当前视频不支持。

#### Nice-to-Have（P1）

1. 允许用户调整双语字幕的相对位置（原文字幕在上 / 翻译在下，或反之）。
2. 允许用户调整双语字幕的字号比例。
3. 记住用户上次是否开启双语模式。

#### Future Considerations（P2）

1. 支持第二行翻译通过不同颜色区分说话人。
2. 支持导出当前视频的双语字幕文本。

### 技术实现要点

YouTube Player 的 `setOption('captions', 'track', ...)` 一次只能设置一条活动字幕轨。要同时显示两种语言，不能依赖 player 同时渲染两条官方字幕。可行方案：

1. **保留官方翻译字幕**：继续用 player API 设置目标语言翻译轨。
2. **手动渲染原文字幕**：通过 `getOption('captions', 'tracklist')` 获取原生字幕轨，再读取其 caption cues（可通过 player 内部事件或网络请求获取 .srt/.vtt 数据），用自定义 DOM 元素覆盖在视频底部显示。
3. **时间同步**：监听 `timeupdate` 或 player 的 `onPlaybackRateChange` 等事件，确保手动渲染的原文字幕与视频当前时间对齐。

### 依赖

- 当前方案2 的 player API 已经能稳定获取字幕轨列表。
- 需要额外研究如何从 YouTube 获取原生字幕的 cue 数据（可能涉及解析 `playerResponse` 中的 `captionTracks` 或拦截字幕网络请求）。

### 风险

| 风险 | 等级 | 说明 |
|------|------|------|
| 原生字幕 cue 获取不稳定 | 中 | YouTube 的字幕数据格式和加载时机可能变化 |
| 自定义字幕层与官方字幕重叠 | 中 | 需要精确计算位置和 z-index |
| 多语言原文字幕选择逻辑复杂 | 低 | 需要判断视频原语言并选择对应原生轨 |

## 未来功能二：Vocabulary Learning（单词点查）

### 问题

用户在看视频时遇到生词，需要暂停视频、打开词典或翻译工具查询，操作链路长，容易打断观看节奏。

### 目标

让用户可以直接点击字幕中的单词，弹出一个小卡片显示释义、发音和例句。

### 用户故事

- 作为一名语言学习者，当我在字幕里遇到不认识的单词时，我想直接点击它查看释义，而不想跳出 YouTube。
- 作为一名备考者，我希望把查过的单词收藏起来，方便后续复习。

### 需求

#### Must-Have（P0）

1. 在字幕渲染层（无论是官方字幕还是双语模式下的自定义字幕）监听单词点击事件。
2. 点击单词后，在当前页面内弹出一个小浮层，显示：
   - 单词释义（中文）
   - 音标 / 发音按钮
   - 1-2 个例句
3. 浮层不遮挡视频主体，且点击外部可关闭。
4. 支持英语、日语等常见学习语言。

#### Nice-to-Have（P1）

1. 收藏单词到本地生词本（`chrome.storage.local`）。
2. 在 popup 或独立页面中查看生词本列表。
3. 标记掌握程度（认识 / 模糊 / 不认识）。
4. 支持划词查询（不仅限于字幕内单词）。

#### Future Considerations（P2）

1. 与 Anki 等第三方工具导出集成。
2. 根据用户收藏的单词推荐相关视频。
3. AI 生成针对该单词的个性化例句。

### 技术实现要点

1. **字幕文本可交互**：
   - 官方字幕的 DOM 结构是 `.ytp-caption-segment`，可以直接在其上监听点击事件。
   - 双语模式下，自定义字幕层天然支持点击事件绑定。
2. **词典数据源**：
   - 方案 A：调用免费的词典 API（如 Free Dictionary API、牛津 API）。
   - 方案 B：用户自行配置翻译 API Key（如 DeepL / OpenAI），通过扩展向第三方服务发请求。
   - 方案 C：本地缓存常用单词释义，减少网络依赖。
3. **发音**：
   - 使用 Web Speech API 的 `speechSynthesis` 播放单词发音。
   - 或集成第三方 TTS 服务。

### 依赖

- 需要用户授权跨域请求（调用词典 API）。
- 如果走用户自备 API Key 方案，需要在 popup 中增加 API Key 设置项。
- 隐私政策需更新，说明扩展会发送用户点击的单词到第三方服务。

### 风险

| 风险 | 等级 | 说明 |
|------|------|------|
| 第三方词典 API 可用性 | 中 | 免费 API 有速率限制或停止服务的风险 |
| 官方字幕 DOM 结构变化 | 中 | YouTube 更新 UI 后选择器可能失效 |
| 用户隐私顾虑 | 低 | 查询单词属于用户行为数据，需明确告知 |

## 未来功能三：AI Video Summary（AI 视频总结）

### 问题

长视频（讲座、播客、教程）的信息密度不均匀，用户希望快速了解视频要点，再决定是否完整观看或重点回看某些段落。

### 目标

为当前 YouTube 视频生成结构化总结：关键要点、学习笔记、词汇表。

### 用户故事

- 作为一名学生，我想在观看 30 分钟讲座前先看到 5 个关键要点，以决定要不要完整看。
- 作为一名自学者，我希望视频结束后自动生成一份笔记和词汇表，方便我复习。
- 作为一名非母语观众，我想看到视频中的核心术语和解释，降低理解门槛。

### 需求

#### Must-Have（P0）

1. 在 popup 中新增「生成视频总结」按钮。
2. 点击后扩展获取当前视频的字幕文本（通过 `playerResponse` 中的字幕数据或网络请求）。
3. 将字幕文本发送给 AI 服务，请求生成：
   - Key points（3-7 条）
   - Notes（结构化笔记）
   - Vocabulary list（核心术语 / 生词表）
4. 在 popup 或新标签页展示总结结果。
5. 支持用户自备 API Key（OpenAI / DeepSeek / SiliconFlow 等兼容端点）。

#### Nice-to-Have（P1）

1. 按视频章节（chapters）分段生成总结。
2. 总结结果支持复制为 Markdown。
3. 保存历史总结到本地，方便回看。
4. 支持自定义提示词模板。

#### Future Considerations（P2）

1. 一键跳转到视频中对应要点的时间戳。
2. 多语言总结输出（如用中文总结英文视频）。
3. 与云端同步历史总结。

### 技术实现要点

1. **字幕文本获取**：
   - 优先从 `playerResponse` 中提取 `captionTracks` 的 URL，下载字幕文本。
   - 回退方案：通过 content script 读取当前已显示字幕的文本（但不完整）。
2. **AI 调用**：
   - 必须由用户自备 API Key，不能硬编码在扩展中。
   - 在 popup 中提供 API Key 输入和端点选择（OpenAI / DeepSeek / Custom）。
   - 请求时使用用户 Key 直接向 AI 服务商发送，扩展不中转。
3. **长文本处理**：
   - 长视频字幕可能超出模型上下文限制，需要分段摘要再聚合。
4. **结果展示**：
   - 可在 popup 内用折叠面板展示三类结果。
   - 或打开一个独立的 `summary.html` 页面，展示更完整的内容。

### 依赖

- 用户必须提供自己的 AI API Key。
- 扩展需要 `https://*/*` 的主机权限（用户自定义端点）或至少覆盖常见 AI API 域名。
- 隐私政策必须明确说明：扩展仅在用户主动触发时，将视频字幕文本通过用户自己的 API Key 发送到用户配置的 AI 服务，开发者不收集数据。

### 风险

| 风险 | 等级 | 说明 |
|------|------|------|
| 字幕文本获取失败 | 高 | 部分视频无字幕，或字幕 URL 格式变化 |
| 长视频 token 成本 | 中 | 用户需自行承担 AI 调用费用 |
| AI 输出质量不稳定 | 中 | 不同模型对总结质量差异大 |
| 隐私/合规审核 | 中 | Chrome Web Store 对 AI 功能的数据说明要求严格 |

## 功能优先级与路线图建议

### 优先级排序

| 优先级 | 功能 | 理由 |
|--------|------|------|
| P1 | Dual Subtitle Mode | 与现有字幕能力最贴近，技术依赖最少，用户价值明确 |
| P2 | Vocabulary Learning | 依赖双语字幕的字幕交互能力，是双语模式的自然延伸 |
| P3 | AI Video Summary | 价值高但实现复杂，依赖外部 AI 服务和用户配置 |

### 建议路线图

**Now（当前阶段）**

- 继续优化核心字幕翻译的稳定性（方案2 的验证逻辑优化）。
- 完成 popup UI 简化（删除「应用」按钮和「记住语言偏好」复选框）。

**Next（下一个阶段）**

- 启动 Dual Subtitle Mode 的设计与开发。
- 调研原生字幕 cue 数据的获取方式。
- 设计双语字幕的自定义渲染层。

**Later（远期）**

- 在双语字幕基础上增加 Vocabulary Learning。
- 评估 AI Video Summary 的 AI 服务集成方案（用户自备 Key）。
- 更新隐私政策和商店描述，覆盖新增功能的数据使用说明。

## 与当前技术路线的关系

当前 SubtitleMate 已选择 **方案2：操作 YouTube Player 内部对象**。这一路线对未来功能的影响：

1. **Dual Subtitle Mode**：需要基于方案2 获取 `tracklist` 和原生字幕数据，同时保留翻译轨。自定义渲染层与方案2 不冲突。
2. **Vocabulary Learning**：依赖字幕文本的可交互性。方案2 本身不直接提供「可点击字幕」，但官方字幕 DOM 仍然可以被监听点击。双语模式下的自定义字幕层更易实现。
3. **AI Video Summary**：与方案2 关系较弱，主要依赖字幕文本获取。但方案2 已经建立了对 player 内部结构和 `playerResponse` 的理解，有助于提取字幕 URL。

---

## 非目标（明确不做的范围）

为避免范围蔓延，以下方向暂不考虑：

1. **非 YouTube 平台支持**：当前产品聚焦 YouTube，扩展到其他视频平台会显著增加维护成本。
2. **实时语音转字幕**：不替代 YouTube 原生字幕，不做语音识别。
3. **社区共享字幕**：不做字幕上传、评分、下载平台。
4. **移动端支持**：Chrome 扩展主要针对桌面端，移动端适配不在近期规划内。
5. **自动总结后自动跳转到视频结尾**：不干扰用户正常观看流程。

## 成功指标

| 指标 | 目标 | 说明 |
|------|------|------|
| 双语字幕功能使用率 | > 30% 的活跃用户尝试过 | 反映功能吸引力 |
| 双语字幕开启后 7 日留存 | 相比未开启用户 +10% | 反映核心价值 |
| 单词点查日均次数 | > 2 次/活跃用户 | 反映学习场景粘性 |
| AI 总结功能完成率 | > 70% 的点击能成功生成总结 | 反映功能稳定性 |
| Chrome Web Store 评分 | 维持或提升 | 反映整体产品满意度 |

## 待确认问题

| 问题 | 负责方 | 说明 |
|------|--------|------|
| AI Video Summary 是否默认支持所有语言的字幕总结？ | 产品 / 工程 | 需要考虑多语言输入输出的质量 |
| Vocabulary Learning 是否必须依赖双语字幕才能使用？ | 产品 | 如果只做单语字幕点查，范围会小很多 |
| 是否允许用户不配置 API Key 就使用 AI 总结？ | 产品 / 商业 | 若由开发者承担 API 费用，需重新评估商业模式 |
| 双语字幕的自定义渲染是否会被 YouTube UI 更新频繁破坏？ | 工程 | 需要评估维护成本 |

---

## 结论

SubtitleMate 的未来功能应沿着「自动字幕 → 双语对照 → 单词学习 → AI 总结」的路径逐步演进。每一项新功能都应建立在当前已落地的内部 API 路线上，避免重新引入已被废弃的 UI 模拟点击方案。

建议明天先完成核心稳定性的优化，再启动 Dual Subtitle Mode 的预研和原型验证。
